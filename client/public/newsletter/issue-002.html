① Main Story

Stop Winging It: How Claude MD Files Actually Work

Most people are either skipping Claude MD files entirely or using one file for everything — and both are costing them time on every single project.

If you've been using Claude for projects, you've probably run into the Claude MD file — or heard it mentioned and nodded like you knew what it was. Plain version: a Claude MD file is a set of written instructions that lives inside your Claude project. It tells Claude who you are, what the project is, how you want it to behave, and what rules to follow. Think of it as the briefing document you hand a new hire before they touch anything.

Here's where most people get it wrong — they either skip the MD file entirely and re-explain everything every session, or they have one global file they never touch and expect it to handle every project. Cheryl put it plainly: the global MD is your baseline — your name, your work style, how you like Claude to communicate. It stays put. Your project MD is the specific job brief — the client details, the tech stack, the constraints, the output format. They serve different purposes and both need to exist separately.

The mistake that kills consistency: cramming everything into one file. When brand voice, project specs, technical constraints, and output format all live in the same place, Claude doesn't know what's a standing rule and what's project-specific. Separate them and your outputs get dramatically more consistent — because Claude finally knows what's permanent and what's contextual.

  • Global MD = standing rules. Your name, your role, communication preferences, things always true no matter the project. Set it once, rarely touch it.
  • Project MD = job brief. The specific build — client info, tech stack, constraints, audience, output format. Update it as the project evolves.
  • Let Claude update its own MD. Mid-project, just say "add this to my project Claude MD." Claude suggests the update, you paste it in. Keeps the file current without a full rewrite every week.
💼 How does this apply to your business?

Every client build you do should have its own project MD. That file holds the client's business details, voice agent rules, CRM setup, pain points, pricing — everything Claude needs without you re-explaining every session. When the client calls with a change, you update the MD and every subsequent conversation already knows. That's the difference between consulting at $500/month and retaining at $2,500/month.

② Also This Week

Big Steele's Pre-Demo Audit: Don't Go Live Without This

One of the most valuable things shared in the group this week didn't get nearly enough attention. Big Steele dropped a detailed prompt framework for running a QA audit on your app or agent before you demo it to an investor, client, or prospect. The framing was sharp: assume your reviewer is smart, skeptical, and actively looking for reasons to pass. They'll click things in the wrong order. They'll use a stale session. They'll find the one broken thing in the first 15 minutes.

The audit runs through four buckets: demo killers (what would visibly embarrass you on screen), credibility leaks (things that don't break the demo but signal an amateur build), the golden path (what the reviewer needs to see to say yes), and failure modes under conditions you can't control — hotel wifi, projector color, one-handed phone use. Run your build through all four before every live demo.

The core rule embedded in the prompt: if a bucket is empty, the audit isn't done — it means you haven't looked hard enough yet. That's the standard that wins investor meetings and closes clients on demo calls.
